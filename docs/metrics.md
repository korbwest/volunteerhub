# Метрики качества

## Показатели

| Метрика | Источник | Способ фиксации |
| --- | --- | --- |
| Ошибки и предупреждения линтера | Ruff JSON и ESLint JSON | Автоматически по backend и frontend |
| Покрытие строк кода | pytest-cov JSON и Vitest coverage summary | Автоматически, отдельно по частям приложения |
| Пройденные и упавшие тесты | pytest и Vitest JUnit XML | Автоматически; пропуски учитываются отдельно |
| Время выполнения тестов | Поле time в отчётах JUnit | Автоматически, секунды по каждому набору |
| Частота коммитов | GitHub Insights | Вручную сохраняется значение и скриншот за выбранный период |

Все нарушения Ruff учитываются как ошибки; предупреждения для него равны нулю по принятой классификации. ESLint предоставляет отдельные счётчики ошибок и предупреждений. Форматтеры проверяются отдельно и не включаются в число нарушений линтера.

Покрытие строк равно 100 × covered / total. Проценты backend и frontend не усредняются. Время JUnit не равно длительности всего пайплайна; вложенные suites не суммируются дважды. Служебные unittest проверяют инструменты и не входят в число тестов приложения.

`scripts/metrics.py` объединяет отчёты. Отсутствующий файл означает `null`, а не нулевое число ошибок. `automated_complete` показывает наличие четырёх автоматических групп; при неполноте скрипт завершится ошибкой. `complete` остаётся false, поскольку пятую метрику нужно подтвердить отдельным замером Insights.

## Частота коммитов

В GitHub Insights → Commits выберите график коммитов и зафиксируйте показанный интервал. Основная единица — коммитов за неделю. При необходимости вычислите коммитов в день как N / D, где N — число коммитов, D — календарные дни выбранного интервала, включая дни без коммитов. Запишите границы периода и область истории, показанную GitHub. Для итогового замера используйте основную ветку после слияния.

Rebase and merge сохраняет отдельные коммиты, но обновляет их SHA и сведения о времени фиксации. Первоначальный перенос прототипа множеством коммитов не характеризует равномерную интенсивность разработки; это ограничение необходимо учитывать при анализе.

В этом варианте автоматизированы четыре выбранные группы, а пятая фиксируется вручную. Это не полное выполнение требования лабораторной об автоматическом сборе не менее пяти метрик; использование Insights необходимо согласовать с преподавателем.

## Контрольные точки

| Этап | Момент замера |
| --- | --- |
| lab5 | Завершение настройки репозитория и проверок |
| lab6 | Демонстрационный прототип |
| lab7 | Расширенное автоматическое тестирование |
| final | Полная реализация и итоговый отчёт |

Если утверждённый график содержит промежуточные этапы, измерения выполняются и на них. Не проставляйте будущие значения заранее.

После появления workflow в основной ветке: Actions → Quality → Run workflow → выбрать main и stage. Нажатие кнопки отмечает этап; вычисления четырёх групп выполняются автоматически. Сохраните артефакт `quality-metrics`, URL запуска, SHA и скриншот Insights в `docs/measurements/<stage>-<sha>/`. Отчёт относится к измеренному SHA, а не к последующему коммиту с сохранёнными файлами. Артефакт `prototype-build` содержит сборку той же версии.
