# Работа с исходным кодом

## Ветвление

Используется GitHub Flow. `main` содержит принятую версию проекта. Изменения выполняются в короткоживущих ветках, созданных от актуальной `main`:

- `feat/...` — функциональность;
- `fix/...` — исправления;
- `test/...` — тесты;
- `docs/...` — документация;
- `ci/...` — автоматизация проверок и сборки.

Первоначальный прототип подготовлен в `feat/initial-prototype`. Постоянной ветки `develop` нет.

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/project-search
```

## Коммиты

Формат сообщения: `type(scope): описание`. Область `scope` необязательна. Заголовок не длиннее 100 символов. Один коммит соответствует одной связанной задаче.

```text
feat(db): add user and project models
feat(auth): add authentication endpoints
test(projects): cover project access and filtering
fix(auth): correct login validation
docs: describe local setup
```

Используются типы `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Для несовместимого изменения после типа или области указывается `!`, а причина описывается в сообщении.

Сообщения проверяются локальным hook `.githooks/commit-msg` и заданием `commits` в GitHub Actions. После клонирования включите hook:

```powershell
git config core.hooksPath .githooks
```

Локальный hook можно обойти, поэтому обязательной серверной проверкой служит CI. Скрипт `scripts/check_commits.py` проверяет все новые коммиты pull request; при первой отправке ветки проверяется вся доступная история.

## Pull request и слияние

После локальных проверок рабочая ветка отправляется на GitHub и открывается pull request в `main`. В описании указываются изменения, способ проверки и известные ограничения.

Способ слияния — **Rebase and merge**. Он сохраняет отдельные коммиты в основной истории без дополнительного merge-коммита. Перед слиянием необходимо проверить сообщения всех коммитов и результаты тестов. После слияния рабочая ветка удаляется.

Защита `main` и обязательные проверки должны быть настроены на этапе подготовки CI. До этого слияние первоначального прототипа не выполняется.

В Settings → Branches создайте правило для `main`: требовать PR, успешные `commits`, `backend`, `frontend`, `metrics`, `build`, актуальность ветки и запрет обхода правил. Не разрешайте force push и удаление основной ветки. В индивидуальном проекте обязательное чужое одобрение не требуется. Имена проверок выбирайте из результатов первого запуска Actions.

## Релиз

После успешных проверок и слияния PR обновите локальную `main`, затем создайте тег:

```powershell
git switch main
git pull --ff-only origin main
git tag -a v0.1.0 -m "Initial prototype and quality checks"
git push origin v0.1.0
```

На GitHub откройте Releases → Draft a new release, выберите существующий тег `v0.1.0`, опишите возможности и ограничения. Прикрепите артефакты сборки и измерений из успешного запуска Quality для того же SHA и опубликуйте релиз. Создание релиза выполняется вручную; автоматическое развёртывание не предусмотрено.
